# MuSiQue 顺序链支持门实验（v66）

## 1. 结论

v66 针对 v65 暴露的“高置信局部 span 不等于完整多跳链”问题，冻结了一个更严格的链级支持门：使用官方分解问题作为 oracle 计划，但执行时禁止读取分解答案和 supporting 标记，只允许把固定 RoBERTa 模型上一跳预测出的 span 替换到后续 `#1/#2` 占位符；所有跳都严格超过 v64 阈值 `0.974609375` 时，案例才通过。

600 条与 v65 来源承诺互斥的开发样本上，顺序链门把无答案拒绝率从直接问句门的 `0.526667` 提高到 `0.816667`，并拒绝了 `0.697183` 的直接门误放行案例；但答案通过率从 `0.610000` 降到 `0.390000`。最终平衡准确率只从 `0.568333` 提高到 `0.603333`，配对正确性增益为 `+0.035000`，95% bootstrap 区间为 `[-0.015000,+0.085000]`。

预注册门槛要求链门平衡准确率至少 `0.72`、答案通过率至少 `0.60`、相对直接门增益至少 `0.10` 且区间下界高于 `0.05`；这些条件均未通过。因此状态冻结为：

`MUSIQUE_V66_SEQUENTIAL_CHAIN_DEVELOPMENT_SUPPORT_NOT_ESTABLISHED_STOP_BEFORE_CONFIRMATION`

确认阶段未打开；v66 不得用于后验调整阈值、链规则、门槛或选型。选择器、CANARY、DEFAULT 均不授权，Gate 2 保持 `NO-GO/SHADOW`。

## 2. 冻结边界与样本

- 目标仍为官方 MuSiQue revision `922ac98f19a201998dbdae6d7f2887a5258dbdeb` 的 `musique_full_v1.0_train.jsonl`，许可为 CC BY 4.0。
- 文件在 v65 已被解析，因此 v66 不声称“首次访问数据源”；但协议、来源、样本盐、公式、门槛、实现和纯合成测试均在选择任何 v66 来源承诺前冻结，剩余案例没有模型预测或 gold 指标。
- v66 排除 v65 无效运行的 300 个来源承诺和修正运行的 600 个来源承诺，合计 900 个唯一来源；实际排除配对变体 1,800 行，最终重叠为 0。
- 继续排除组合问题或任一分解问题与 SQuAD2 train 规范化题面精确相同的 5,388 行。
- 以固定 SHA-256 奇偶规则先把同一来源 ID 的答案/无答案配对变体分配到唯一答案状态，再确定性选择答案/无答案各 300 条。
- 600 个来源 ID 全部唯一，每例 20 个段落；2/3/4-hop 为 460/114/26 例。

精确题面排除不能排除释义、上下文或预训练重叠；该实验不是严格独立模型训练确认。

## 3. 执行规则

### 3.1 公平直接门

直接基线沿用 v65：把组合问题分别输入全部 20 个段落，取有限 `null-vs-span` margin 最大值；仅当最大值严格大于 `0.974609375` 时通过。

### 3.2 顺序链门

1. 按官方 `question_decomposition` 列表顺序执行 2—4 个分解问题；
2. 执行器只能看到分解问题文本和顺序，不能看到分解答案、`paragraph_support_idx` 或段落 `is_supporting`；
3. 后续问题中的 `#k` 只能用第 k 跳固定模型选择的 span 替换；
4. 每个已解析问题仍对全部 20 个段落运行同一固定模型并取最大 margin；
5. 任一跳未严格超过固定阈值、输出无效或缺少前驱预测，当前及后续链失败关闭；
6. 只有所有跳均通过，案例才判为支持充分。

目标数据上学习或调整的参数为 0。模型、tokenizer、阈值、段落聚合和门槛均未改变。

## 4. 执行完整性

初始 `prepare` 命令在模块导入时因仓库根目录未加入 `sys.path` 而失败。失败发生在参数解析、来源验证和目标文件打开前：读取 v66 目标行数为 0，未选择来源承诺、未运行模型、未连接 gold。执行前勘误只增加仓库根目录导入路径并更新默认实现登记，不改变实验公式或门槛。

修正后执行环境为 Python 3.10.20、PyTorch 2.4.1+cu124、Transformers 4.46.3、NVIDIA GeForce RTX 4060 Ti，FP16、batch size 16。执行量为：

- 直接组合问题：12,000 条段落 QA；
- 第 1 跳：12,000 条；
- 第 2 跳：7,960 条，202 例因前驱未通过而停止；
- 第 3 跳：820 条，仅 41/140 个三跳及以上案例继续执行；
- 第 4 跳：20 条，仅 1/26 个四跳案例继续执行。

全部 QA 与链决策完成后才连接 answerability。无效链输出为 0。

## 5. 冻结结果

| 指标 | 直接组合问题门 | oracle 计划顺序链门 |
| --- | ---: | ---: |
| 答案通过率 | 0.610000 | 0.390000 |
| 无答案拒绝率 | 0.526667 | 0.816667 |
| 平衡准确率 | 0.568333 | 0.603333 |

配对正确性增益为 `+0.035000`，95% CI `[-0.015000,+0.085000]`。直接门误放行 142 个无答案案例，顺序链拒绝其中 `0.697183`。无答案分层拒绝率为：

- 2-hop：`0.779221`（231 例）；
- 3-hop：`0.944444`（54 例）；
- 4-hop：`0.933333`（15 例）。

结构完整性、无答案拒绝、误放行陷阱拒绝和全部 hop 分层安全门通过；但答案通过率、总体平衡准确率、点增益与置信区间门失败。

## 6. 机制解释

v66 证明链级执行能显著加强对断链案例的保守拒绝，但“每一跳都使用同一个 SQuAD2 单段阈值并做严格合取”会累积假阴性。两跳案例必须连续两次通过，三跳和四跳还要承受预测 span 误差向后传播；第 1 跳已有 202/600 例停止，后续链可用率快速下降。因此无答案安全性改善被答案召回损失抵消，不能形成稳定的总体增益。

这表明后续研究需要在新的互斥数据上区分两类问题：

1. 单跳 span 是否得到段落支持；
2. 多跳链是否在允许适度单跳不确定性的同时保持实体传递与证据覆盖一致。

不能在 v66 案例上放宽“全跳合取”、降低阈值或选择更有利的跳数组合后再称为确认。

## 7. 结论边界

v66 支持“oracle 分解计划 + 顺序预测执行可提高断链拒绝，但严格同阈值全跳合取过度保守”的负向机制结论。它不构成：

- 自动问题分解能力证明；
- 官方 MuSiQue 排名或答案生成结果；
- FRC-RAG 与检索基线的效用比较；
- 真实 SetR 复现；
- 严格独立模型训练、洪水领域专家或生产放行证据。

确认集、检索评分和选择器采用均未授权，Gate 2 继续为 `NO-GO/SHADOW`。
