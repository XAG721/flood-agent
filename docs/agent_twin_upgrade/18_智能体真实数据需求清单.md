# AgentTwin Flood 智能体真实数据需求清单

## 1. 文档目的

本文档用于说明当前 demo 如果升级为真实防汛业务系统，智能体具体需要哪些数据。数据范围参考县级防汛应急预案中的典型闭环：组织指挥、责任落实、风险识别、监测预警、预警叫应、会商研判、响应行动、转移安置、信息报送、善后复盘。

智能体要实现更强能力，不能只接雨量和水位，而要接入一整套应急上下文：

```text
预案规则 + 责任体系 + 实时态势 + 风险对象 + 重点人群
+ 群众反馈 + 网格员上报 + 队伍物资 + 特殊设施
+ 叫应反馈 + 任务闭环 + 信息报送 + 审计证据
```

## 2. 数据设计原则

1. 以预案为骨架：响应等级、叫应对象、报送时限、责任人、转移条件等必须结构化。
2. 以对象为中心：从区域级风险下钻到学校、医院、养老院、危化企业、尾矿库、水利工程等对象。
3. 以闭环为目标：每条预警、每次叫应、每个任务都要有状态、反馈、超时和完成记录。
4. 以证据为约束：智能体建议必须能追溯到传感器、上报、预案条款、历史案例或人工确认。
5. 以隐私最小化为前提：重点人群信息应脱敏、分级授权，只暴露救援和转移所需字段。

## 3. 数据总览

| 数据类别 | 主要用途 | 优先级 |
|---|---|---|
| 组织指挥与责任人数据 | 判断谁负责、谁审批、谁被叫应 | P0 |
| 预警响应规则数据 | 判断是否启动、调整或结束响应 | P0 |
| 实时气象水文内涝数据 | 判断风险强度、趋势和影响时间窗 | P0 |
| 风险隐患与空间对象数据 | 判断风险在哪里、会影响哪些对象 | P0 |
| 重点对象画像数据 | 生成对象级预警和处置建议 | P0 |
| 重点人群与个体救援数据 | 支撑转移避险和上门确认 | P0 |
| 群众反馈与网格员上报数据 | 发现传感器之外的现场风险 | P0 |
| 队伍物资装备数据 | 判断处置方案是否可执行 | P0 |
| 避险转移与安置数据 | 生成转移路线、批次和安置方案 | P0 |
| 叫应反馈数据 | 跟踪叫醒、回应、执行情况 | P0 |
| 任务执行闭环数据 | 跟踪处置是否完成 | P0 |
| 信息报送与发布数据 | 支撑首报、续报、权威发布 | P0 |

## 4. 组织指挥与责任人数据

智能体需要知道“谁负责、谁决策、谁执行、谁反馈”。

### 4.1 指挥机构数据

- `command_org_id`：指挥机构ID
- `name`：机构名称
- `level`：县级、乡镇级、村社区级、专项分指挥部
- `parent_org_id`：上级机构
- `jurisdiction_area`：管辖区域
- `duty_scope`：职责范围
- `activation_condition`：启动条件
- `office_location`：办公地点
- `contact_channels`：电话、短信、工作群、政务平台
- `on_duty_status`：正常值守、加强值守、集中办公、前方指挥

### 4.2 责任人数据

- `person_id`：人员ID
- `name`：姓名
- `role`：指挥长、值班员、乡镇责任人、村社区责任人、网格员、户责任人
- `org_id`：所属机构
- `area_id`：负责区域
- `object_ids`：负责对象，如水库、河道、学校、低洼区
- `phone`：电话
- `backup_contact`：备用联系人
- `duty_shift`：值班班次
- `is_on_duty`：是否在岗
- `last_ack_at`：最近一次确认时间
- `availability_status`：可联系、未响应、离岗、替班

智能体用途：

- 判断预警需要叫应到谁。
- 判断某个处置动作需要谁审批。
- 判断责任人是否超时未反馈。
- 在响应升级时生成会商和通知名单。

## 5. 预警与响应规则数据

智能体需要将实时数据映射到响应等级和动作清单。

- `rule_id`：规则ID
- `hazard_type`：暴雨、洪水、山洪、地质灾害、城市内涝
- `warning_level`：蓝、黄、橙、红
- `response_level`：四级、三级、二级、一级
- `trigger_conditions`：启动条件集合
- `metric_thresholds`：雨量、水位、积水面积、灾情范围等阈值
- `required_consultation_units`：需要参加会商的单位
- `required_actions`：必须动作
- `optional_actions`：建议动作
- `approval_required`：是否需要审批
- `reporting_frequency`：报送频率
- `termination_conditions`：结束条件
- `source_plan_id`：来源预案
- `source_clause`：来源条款

智能体用途：

- 自动判断是否建议启动响应。
- 自动生成“响应行动清单”。
- 检查当前动作是否符合预案。
- 在预警解除、河道水位回落、任务结束时建议响应调整或结束。

## 16. 特殊设施运行状态数据

以下数据不能只写“运行正常/异常”，必须拆到智能体能判断风险和动作的字段。每类特殊设施都建议同时记录：基础画像、实时状态、异常判定、建议动作、责任单位和更新时间。

### 16.1 医院运行状态

用途：判断急救通道、医疗连续性、病患转移和医疗资源支援。

字段建议：

- `hospital_id`、`name`、`hospital_level`、`location`
- `emergency_entrance_status`：通畅、积水、拥堵、封闭
- `ambulance_route_status`
- `inpatient_count`
- `icu_bed_count`、`icu_occupied_count`
- `dialysis_patient_count`
- `oxygen_supply_hours`
- `backup_power_hours`
- `generator_status`
- `medicine_stock_status`
- `medical_staff_on_duty`
- `emergency_team_available`
- `basement_or_low_level_facility_status`
- `water_supply_status`
- `communication_status`
- `patient_transfer_capacity`
- `external_support_needed`
- `hospital_incident_contact`
- `last_update_at`

| 状态项 | 建议采集频率 | 异常判定 | 智能体触发动作 | 责任单位 |
|---|---|---|---|---|
| 急诊入口和救护车通道 | 10-15分钟 | 积水、拥堵、封闭、救护车无法抵达 | 生成道路保障和排水任务 | 卫健、公安交警、城管 |
| ICU和重症病区 | 30分钟 | 床位满载、备用电源不足、氧气供应不足 | 标记为最高保障对象，建议调度医疗资源 | 卫健、医院 |
| 备用电源 | 30分钟 | 可支撑时间低于4小时或发电机异常 | 准备发电车、燃油和抢修队 | 供电、应急、医院 |
| 地下设备间 | 10-30分钟 | 进水、倒灌、排水泵失效 | 生成地下空间封控和设备抢护任务 | 医院、城管、水务 |
| 病患转移能力 | 30-60分钟 | 需转移人数超过车辆或医护能力 | 建议分批转移，计算车辆、担架、医护需求 | 卫健、应急、交通 |

## 17. 增强型智能体可接入数据

- 视频AI识别：积水、人车滞留、道路中断、井盖异常。
- 无人机巡查影像：低洼区、河道、堤防、水库、山洪沟。
- 交通导航数据：拥堵、封路、绕行时间。
- 手机信令或人流热力：景区、学校、车站、商业区人员聚集。
- 舆情数据：群众集中反映点、谣言、恐慌情绪。
- 水动力模型：积水扩散、漫溢路径、到达时间。
- 高精度地形和三维城市模型。
- 保险理赔、灾损评估和救助数据。

## 19. 最小落地优先级

### P0：真实业务闭环必须具备

- 组织责任人
- 预警响应规则
- 实时雨量水位
- 风险隐患点
- 重点对象画像
- 重点人群脱敏台账
- 队伍物资装备
- 避险场所和路线
- 群众反馈与网格员上报
- 叫应反馈
- 任务执行闭环
- 信息报送规则
- 智能体运行审计

### P1：真实应急能力增强

- 医院、学校、养老院运行状态
- 危化品、尾矿库、水利工程状态
- 交通、电力、通信、供水等生命线状态
- 视频识别
- 泵站闸门状态
- 预警发布回执
- 历史案例和复盘库

### P2：高级智能决策增强

- 水动力模型
- 三维城市模型
- 人流热力
- 无人机巡查
- 舆情分析
- 自动灾损评估
- 跨区域资源调度
- 长期策略学习

## 20. 总结

智能体需要的数据不是单一的气象水情数据，而是一整套防汛应急上下文。只有这些数据被结构化、可追溯、可更新，智能体才能从“问答助手”升级为真正可用于防汛指挥的人机协同系统。
